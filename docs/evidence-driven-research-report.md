# 证据驱动的行业研究系统：方法论与验证结果

**版本**：v1.0（2026-08-02）
**对应代码状态**：`main @ ba07d3a`（CI 全绿，分支保护已启用）
**素材来源**：`CONTEXT.md`、`PRODUCT.md`、`docs/evaluation/` 证据包

---

## 摘要

Fund Engine 是一套证据驱动的行业研究系统，目标不是"生成一份看起来完整的研究报告"，而是让研究员能够持续回答四个问题：当前行业命题得到什么支持、受到什么反驳、仍缺什么证据、判断如何随时间变化。系统以**不可变证据账本**为核心，AI 判断与人类复核以分离记录共存、机器结论永不被覆盖；所有判断可沿"评估 → 快照 → 证据关系 → 原子陈述 → 原文片段"链条逐层回溯到冻结原文。

本文总结系统的方法论、关键工程机制与验证结果。核心数据：混合召回将金标证据 recall@20 从 **0.7333 提升至 1.0000**（4 条金标陈述全部找回，0 丢失）；发布门禁 10 项检查中 9 项通过、1 项按设计跳过；验证体系覆盖 218 个后端测试、62 个前端测试、32 条端到端用例，并已全部接入 CI 与 main 分支保护。

---

## 1. 背景与问题

专业行业研究员的日常不是浏览一次性报告，而是持续处理新材料、审核机器提议、维护行业命题、识别证据冲突，并把已验证的研究关系穿透到公司、股票、估值与基金披露持仓（`PRODUCT.md`）。

现有工具的三个结构性缺陷：

1. **结论与证据脱节**：AI 生成的研究结论无法回溯到具体原文位置，无法回答"这句话凭什么这么说"。
2. **人机边界模糊**：机器草稿与人工结论混在一起，复核动作覆盖原始输出，审计无从谈起。
3. **时间语义缺失**："当前状态"掩盖了信息可见性——站在历史时点回放时，后公开的材料不应出现。

系统的设计回应是三条不可妥协的原则：**证据始终可追溯**、**AI 与人工边界可见**、**时点可回放**。

## 2. 方法论：不可变账本上的研究语义

### 2.1 核心词汇表（Ubiquitous Language）

系统对研究对象做了严格的语义区分（`CONTEXT.md`），每个概念都有明确的"反义词"防止退化：

| 概念 | 定义 | 明确不是 |
|---|---|---|
| **Thesis** | 可检验、可证伪、有时间边界的命题 | 主题、结论、推荐 |
| **AIAssessment** | 基于冻结证据快照的**不可变临时** AI 判断，在人工决策前始终显著标记为未复核 | 最终结论、置信分数 |
| **ReviewDecision** | 不可变人工决策，确认/修改/驳回并记录理由，**不替换机器输出** | 编辑、审批标志、可变状态 |
| **Proposal** | 机器或人工提出的关系建议，经人工复核发布前不是正式研究关系 | 证据、已批准关系 |
| **SourceStatement** | 来源明确做出的原子陈述（披露事实/管理层归因/预测/研究观点） | 客观事实 |
| **EvidenceLink** | 解释某陈述为何在特定时间与范围内支持/反驳/补充某命题的**带版本论证** | 自动 SUPPORTS 边、语义相似度 |
| **EvidenceSnapshot** | 一次 AI 评估在其截止时点可见的冻结集合 | 当前数据库状态 |

### 2.2 三条架构原则

**原则一：一切判断可回溯到冻结原文。** 每个 `AIAssessment` 必须能沿 `评估 → EvidenceSnapshot → EvidenceLink → SourceStatement → SourceSpan` 链条追到带确切位置（页区/段落/表格单元格/字符区间）的原文片段。这不是产品文案，而是门禁检查 3（`assessment_source_spans_complete`）的强制约束。

**原则二：AI 与人工是两类记录，不是两种状态。** AI 结论永远标记为临时（`displayed_as_provisional = True`）；人工复核以独立的 `ReviewDecision` 追加，原始机器结论保持原样。门禁检查 6、7 分别强制"边界可见"与"每个 AI 判断都有人工复核记录"（review_coverage == 1.0）。

**原则三：时点可回放。** 历史截止日之后的材料（含基金持仓披露）必须从技术视图中消失。门禁检查 5（`future_material_excluded`）用 cutoff=2026-04-01 验证后公开披露不出现在敞口计算中。

### 2.3 谨慎的投资映射

研究关系向证券的映射经过显式的 `ThemeRole`（公司在主题中的角色，含适用范围与期间）与 `Expression`（考虑估值、敞口、新鲜度与约束后的敞口表达）两层抽象——敞口表达**本身不是推荐**。基金侧只使用**带报告期与发布日期双时间戳**的持仓披露（门禁检查 4 强制），杜绝"实时持仓"幻觉。

## 3. 系统架构

```
┌─────────────────────────────────────────────────────┐
│ 前端（React 18 + Vite，PrototypeShell 主题化外壳）      │
│ 主题 → 工作台 → 审核中心 → 数据中心 → 快照版本           │
├─────────────────────────────────────────────────────┤
│ 契约层（OpenAPI → openapi-typescript 生成 v1.ts）      │
├─────────────────────────────────────────────────────┤
│ 后端（FastAPI + SQLAlchemy，/api/v1）                 │
│ RecallService │ ExposureService │ WorkbenchService   │
│ ComplianceGate │ ResearchOpsKPI │ PdfTextService     │
├─────────────────────────────────────────────────────┤
│ 不可变账本（sqlite/PostgreSQL，Alembic 迁移）          │
│ 可选投影（Neo4j，可从账本完整重建）                     │
└─────────────────────────────────────────────────────┘
```

前端与后端通过 OpenAPI 契约生成类型（`frontend/src/contracts/v1.ts`），前端另有内存 mock 适配器，使界面开发与 e2e 测试不依赖后端可用性。

## 4. 关键工程机制

### 4.1 混合召回（P0）

问题：粗粒度分词器把整段中文连续文本切成单个大 token，使部分金标证据对 BM25 完全不可见（寒武纪命题的 3 条证据即属此列）。

方案：`RecallService` 采用三路融合——BM25（粗 token）+ 本地确定性 char-n-gram TF-IDF 稠密路（恢复子词匹配）+ 词汇信号，以 RRF 融合；`mode="bm25"` 保留为评估基线。真实嵌入后端可在同一契约后替换 `tfidf_rank`。

结果（`backend/scripts/eval_recall_ab.py`，冻结切片离线回放）：

| 指标 | BM25 基线 | 混合召回 |
|---|---|---|
| 总体 recall@10 | 0.6667 | 0.7333 |
| 总体 recall@20 | 0.7333 | **1.0000** |

4 条金标陈述全部找回、0 丢失；脚本内置"混合不得低于基线"的回退守卫，低于基线即退出码 1。

### 4.2 真实 PDF 解析路径（P1）

第二金标案例"锂电储能链"引入了首个真实二进制 PDF fixture（阳光电源年报摘要）。`app/services/pdf_text.py` 将 PDF 文本层解析为可复现的 SourceSpan（CJK 软换行重组、表格块行保留），无文本层 PDF **fail-closed**；文档加盖 `parser_version=pypdf-v1` 戳。门禁检查 9 以 sha256 哈希 + 金标事实双重校验：fixture 被重新生成而未重冻结清单、或 pypdf 升级改变抽取行为，都会使门禁失败。

### 4.3 合规重写回路（P2）

三动作合规契约：REFUSE 类命中直接拒绝、不进入重写；REWRITE 类命中（目标价/收益承诺）获得**恰好一次** LLM 重写（`rewrite-v1` prompt），重写结果经同一合规门复检，残留命中则整个运行拒绝。被修复的评估在 AIRun 上记录 `rewritten_for_compliance`；前端以 422 感知被拒绝的重跑。

### 4.4 研究效能 KPI（P3）

`GET /api/v1/research-ops/kpis` 只从账本推导管理指标，无自报数字：审核吞吐（含按审核人分布与待审队列）、人机一致率（评估级与链路级，无数据时返回 null 而非编造）、判断时滞（证据→AI 判断、AI 判断→首次人工复核，以天计）。支持 `as_of` 时点回放。前端数据中心页以"研究效能"区块呈现，空态诚实显示"暂无数据"。

## 5. 验证体系

验证是本系统的一等公民，分四层：

### 5.1 双金标案例与发布门禁

两个冻结案例（AI 算力链 + 锂电储能链）构成金标语料。发布门禁（`backend/scripts/verify_ai_compute_slice.py`，一键复现 `docs/evaluation/reproduce.sh`）执行 10 项显式检查，fail-closed 设计：数据集清单缺失时**在触碰数据库之前**退出。

| # | 检查 | 语义 | 最新结果 |
|---|---|---|---|
| 1 | document_versions_present | ≥6 份冻结文档版本 | PASS |
| 2 | gold_manifest_matches_ledger | 清单哈希集与账本精确一致（fail-closed） | PASS |
| 3 | assessment_source_spans_complete | 每个评估可回溯至原文片段 | PASS |
| 4 | holding_disclosures_dated | 持仓披露双时间戳齐全 | PASS |
| 5 | future_material_excluded | 历史时点不泄漏未公开材料 | PASS |
| 6 | ai_human_boundary_visible | AI 临时标记 + 复核独立记录 | PASS |
| 7 | review_outcomes_tracked | 复核覆盖率 1.0 | PASS |
| 8 | table_extraction_gold_accuracy | 表格抽取精确复现金标（fail-closed） | PASS |
| 9 | pdf_fixture_parse_gold | PDF 二进制解析端到端复现（fail-closed） | PASS |
| 10 | projection_rebuilds | 图投影可从账本重建（无 Neo4j 时跳过，不判失败） | SKIP |

（来源：`docs/evaluation/reports/20260802T070947Z.json`）

每次运行生成带时间戳的摘要 JSON 并入库留存，形成门禁趋势记录。

### 5.2 单元与契约测试

后端 218 个 pytest（sqlite 默认，pg/neo4j 标记测试无环境时自动跳过）；前端 62 个 vitest（含 mock 适配器行为与 HTTP 适配器契约）。

### 5.3 端到端测试

32 条 Playwright 用例分三层：**结构层**（新外壳全页面锚点与可访问性）、**只读层**（模式无关断言，mock 与真实后端均可通过）、**写入闭环层**（审核决策 → 队列收缩 → 审计入口 → 快照版本页）。写入用例通过 `?client=mock` 测试钩子强制内存适配器，并附带"全程零 API 请求"的防护断言，杜绝决策落入真实后端。

### 5.4 CI 与分支保护

两条 GitHub Actions 流水线：`backend-ci`（pytest + 门禁独立 job）、`frontend-ci`（tsc + vitest + Playwright）。main 分支保护要求全部 4 项检查通过方可合并（strict 模式），禁止 force push 与分支删除。

验证体系自身的价值已被实证：CI 首跑即发现"本地绿、提交树红"的不一致（接口扩展漏同步代理层 + 未提交改动被单独入库），这类问题在分支保护下将无法进入 main。

## 7. 局限与未来工作

**已知局限**：

1. 金标集规模小（2 案例、15 金标陈述），recall@20 = 1.0 不应外推为普遍水平；需要第三、第四案例扩大覆盖。
2. 混合召回的稠密路是确定性 TF-IDF 占位，真实嵌入后端尚未接入（契约已预留）。
3. mock 适配器的快照版本视图是冻结 fixture，"决策 → 新快照数据"联动仅由后端集成测试覆盖。
4. Neo4j 投影检查在 CI 中跳过，图投影回归需带服务的流水线变体。

**未来工作**：

- 嵌入后端替换 `tfidf_rank`，并用同一 A/B 脚本对比；
- 金标集扩充至多行业（半导体、新能源外的新案例）；
- 带 Neo4j/PostgreSQL 服务的 CI 变体，解锁 `pg_only` / `neo4j_only` 测试与门禁检查 10；
- 研究效能 KPI 的趋势视图（当前为单时点）。
