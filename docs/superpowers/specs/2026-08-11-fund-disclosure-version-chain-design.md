# 历史基金披露版本链与真人验收修复设计

## 目标

同一基金、股票和报告期可以保留多份合法、不可变的披露来源，但任何历史读模型都必须以稳定、可解释的规则选出当时有效的一份；研究员也必须能追溯其前序披露。修复真实 UI 验收脚本，使其能完整覆盖这条人工流程。

## 已确认事实与边界

`515050` 对 `601138.SH` 在 `2024-12-31` 已有两份权重均为 `5.33%` 的历史披露：一份于 `2025-01-22` 公开，另一份于 `2025-03-31` 公开。两者都不得删除或覆盖。

本次不把历史持仓变成实时持仓，不推导基金推荐或收益因果，也不自动修改既有不可变披露。外部供应商的原始响应、冻结文件和来源许可继续按现有规则保存。

## 方案

### 1. 披露版本元数据

为 `HoldingDisclosure` 增加两个不可变字段：

- `filing_kind`：`quarterly`、`annual`、`correction`、`other`。旧数据读取为 `other`。
- `supersedes_disclosure_id`：可空、自引用的前序披露 ID。新入库的更高优先级披露可指向同一基金、股票、报告期中较低优先级的已有披露；既有记录不回写。

优先级固定为 `correction > annual > quarterly > other`。同一优先级按较晚 `published_at`，再按较晚 `created_at`，最后按 ID 排序，保证结果确定。

### 2. 入库规则

基金公告标题中出现“更正”时归为 `correction`，出现“年度报告”时归为 `annual`，出现“季度”时归为 `quarterly`，其余为 `other`。新记录只在同一来源已存在时跳过；其他来源仍可作为独立版本写入。

写入前查询同一基金、股票、报告期中较低优先级的现有披露。若存在，创建新记录时写入该前序 ID。若更高优先级记录先于较低优先级入库，仍完整保存两者，但不回写关系；读模型的优先级规则仍给出正确结论。

### 3. 历史读取与页面说明

所有“最新披露”读取先排除 `published_at` 晚于历史 cutoff 的记录，再按上述稳定排序选第一条。因此：

- `2025-01-22` 至 `2025-03-30` 的回放只显示季度披露；
- `2025-03-31` 及之后显示年报披露；
- 同报告期有多份文件时，页面显示“披露版本”与前序披露日期/类型，不把它们误表述为两次持仓。

读取 API/DTO 增加 `filing_kind`、`supersedes_disclosure_id` 及前序摘要，前端基金档案和市场表达显示当前版本及“前序披露”入口。旧记录显示“其他/历史来源”，不会伪造版本关系。

### 4. 真人验收脚本

将“原子陈述审核”的等待条件收窄为 heading role，避免与“原子陈述审核理由”标签共同匹配。脚本仍使用默认 HTTP 客户端、临时 SQLite 后端和浏览器，完成创建案例、冻结资料、原子陈述审核、市场因素、标的和基金披露路径。

## 验收

1. 两份同自然键、不同来源的披露都可保存，且年报记录指向季度前序记录。
2. 截止 `2025-02-01` 选择 2025-01-22 的季度披露；截止 `2025-04-01` 选择 2025-03-31 的年报披露；重复运行结果完全稳定。
3. 真实同步入库的公告标题正确归类；同源重跑仍幂等。
4. 迁移后旧记录可读、没有被更新或删除。
5. 修复后的真实 UI 验收脚本和后端全量测试均通过；前端页面测试、类型检查和构建通过。

## 非目标

- 不自动合并、删除或重写旧披露。
- 不处理定时历史同步策略、生产部署迁移或 PostgreSQL/Neo4j 环境验收；它们保留为后续独立事项。
