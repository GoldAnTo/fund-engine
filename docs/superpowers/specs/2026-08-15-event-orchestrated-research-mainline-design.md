# 事件编排研究主链与透明工作台设计

日期：2026-08-15
状态：已由用户确认

## 1. 设计目的

当前产品已有事件 Case、资料上传、命题与范围、研究运行、资料获取、证据和结论能力，但用户完成上传并确认命题后，仍不知道：

- 系统是否已经开始工作；
- 当前正在处理什么；
- 已经做过哪些搜索、获取、冻结、去重和重试；
- 为什么采用、合并或跳过某份资料；
- 当前是否需要用户操作；
- API、worker 或 scheduler 重启后是否真的会继续。

这不是单纯的前端文案问题，而是缺少一条以事件为主体、由服务端持有真实状态、可以自动推进和恢复的研究主链。

本设计把流程接成：

```text
建立事件
→ 上传或粘贴资料
→ 确认可验证命题与研究范围
→ 自动搜索、获取、冻结和去重外部资料
→ 自动归并证据与判定命题
→ 自动生成带来源的研究报告
→ 自动进入持续监测
```

系统能自行处理时不要求用户点击“继续”。只有研究边界必须改变、关键语义存在歧义或策略明确要求人工判断时才暂停，并只给出一个用户动作。

## 2. 与已有设计和实现的关系

本设计以以下内容为基础：

- `2026-08-12-governed-acquisition-runtime-identity-design.md` 中的资料获取内核、租约恢复、真实身份、Compose 拓扑和 live acceptance 约束；
- `2026-08-07-event-driven-conclusion-workbench-design.md` 中事件为主体、竞争性解释和唯一下一步原则；
- 当前已落地的 SSE/SZSE 搜索、抓取、冻结、去重、Acquisition API、worker、恢复和自动准入内核。

本设计补充并取代上述文档中关于“用户如何从命题确认走到结论”“Case 页面如何显示统一过程”“获取结果何时足够”和“真实浏览器如何验收整条主链”的不完整或互相冲突部分。

资料获取内核仍是独立深模块；Case 编排器只能通过公开 seam 请求和读取获取任务，不能直接调用来源 adapter 或操作获取模块内部表。

## 3. 已确认的产品原则

### 3.1 事件是一级主体

- 每个 Case 对应一个独立事件研究；
- 顶部始终显示当前事件并支持切换其他事件；
- 切换事件后，研究阶段、系统过程、用户下一步、资料台账和结论全部同步切换；
- 不使用全局运行状态替代当前事件自己的运行事实。

### 3.2 系统默认自动推进

- 确认命题与研究范围后立即自动启动资料获取；
- 资料达标后自动进入证据归并、命题判定和报告生成；
- 系统生成且未经人工复核的证据与报告明确标记“系统生成，未经人工审核”；
- 第一版不设置强制人工证据审核或强制结论审核；用户可以主动复核，策略也可对特殊 Case 要求复核，但它们不是默认主链阻塞点；
- 报告生成后自动建立持续监测，不依赖用户再点击“继续”。

### 3.3 一个当前阶段，一个用户动作

- 页面必须明确区分“系统正在做什么”和“你现在应该做什么”；
- 系统自行处理时，用户动作显示为“当前无需操作”，并允许离开页面；
- 需要用户时只显示一个最大阻塞动作，次要选项降级为说明或展开项；
- 技术错误、瞬时失败、去重、阶段衔接和服务恢复不应被包装成人工任务。

### 3.4 过程透明而非黑盒

默认页面要能看到当前操作和最近完成记录；进一步展开后可以看到：

- 每轮检索的证据目标、查询计划、来源和结果；
- 每次获取的状态、最终 URL、抓取时间和原始内容哈希；
- 资料为什么被采用、隔离、跳过或与其他版本合并；
- 当前证据缺口、覆盖变化和下一轮搜索方向；
- 重试、来源切换、租约超时、恢复检查点和重新领取记录；
- 报告中的结论如何回到 EvidenceLink、SourceSpan、DocumentVersion 和 RetrievalArtifact。

## 4. 事件工作台信息架构

事件工作台继续使用现有 `/events/:caseId` 路由和事件内导航，不新增孤立的“流程中心”。默认“研究总览”按以下层级呈现。

### 4.1 顶部事件上下文

- 当前事件选择器；
- Case 编号和当前用户可见的研究阶段；
- 已确认命题、时间窗、主体和研究边界；
- 跳转到命题与冻结范围的入口。

### 4.2 完整研究主链

使用紧凑阶段条显示：

```text
建立事件 → 确认命题 → 主动补证 → 证据归并 → 命题判定 → 报告与监测
```

阶段条只负责方向感；它不代替当前系统过程和事件日志。

### 4.3 系统工作区

首屏回答三个问题：

1. 系统现在正在做什么；
2. 为什么做这件事；
3. 最近做完了什么，结果是什么。

当前操作显示具体对象，例如“正在解析 TSMC 2026 Q2 法说会逐字稿，并与上次指引做差异比对”，不能只显示“运行中”。

最近完成记录按时间追加，不覆盖历史。每条记录至少包含动作、对象、结果、原因和下钻入口。

### 4.4 用户工作区

用户工作区固定回答“你现在应该做什么”：

- 系统可自动推进：显示“当前无需操作”、预计下一阶段和查看实时记录入口；
- 需要研究边界决定：显示缺口、系统尝试历史、推荐决定、影响和一个主按钮；
- 报告已生成：显示报告状态和可选复核入口；未经复核不会伪装为人工确认结果。

### 4.5 资料与决策台账

台账按资料展示来源层级、处理结果、处理理由和可验证记录。至少区分：

- 搜索候选；
- 获取中；
- 已冻结；
- 重复合并；
- 变体冲突；
- 准入；
- 隔离；
- 跳过。

总数只作为运行指标，不能作为研究是否完成的依据。

## 5. 服务端事件编排状态机

### 5.1 唯一事实来源

每个 Case 有一个 `ResearchOrchestration`，至少关联：

- `case_id`；
- 当前 `scope_version`；
- 当前 `research_run_id`；
- 当前内部状态和用户可见阶段；
- 当前检查点；
- 当前系统动作；
- 当前唯一用户动作，可为空；
- 最近成功心跳和恢复状态；
- 状态版本和幂等键。

浏览器只读取服务端生成的统一 workflow projection。不得从旧 Case 状态、前端本地状态、当前配置或另一类运行记录拼出“看起来合理”的运行状态。

### 5.2 内部状态

正常状态：

```text
intake
awaiting_scope_confirmation
planning_acquisition
acquiring
freezing_sources
assessing_coverage
synthesizing_evidence
adjudicating_thesis
generating_report
monitoring
```

可恢复和中断状态：

```text
retry_wait
recovering
needs_scope_decision
exhausted
cancelled
failed
```

内部状态可以比页面阶段更细，但映射必须是服务端版本化规则。页面不得自行推断映射。

### 5.3 自动转换

- `awaiting_scope_confirmation` 只有用户确认命题和范围后才能离开；
- 确认命令在同一事务中写入新 `scope_version`、推进 orchestration、追加事件并写入下一任务 outbox；
- acquisition 覆盖达标后自动进入证据归并；
- 证据归并完成后自动判定命题；
- 判定完成后自动生成报告，并在无策略阻塞时自动进入 monitoring；
- 每次转换都追加事件并建立可恢复检查点；
- 所有副作用使用稳定幂等键，允许安全重放。

### 5.4 何时才找用户

只有下列情况进入 `needs_scope_decision`：

- 关键实体、时间窗、指标或命题语义无法安全确定；
- 达到限定检索轮次后仍缺关键证据，继续需要扩大来源类型、时间窗或研究主体；
- 出现无法用现有判定标准处理的关键证据冲突；
- Case 策略明确要求某一步人工确认。

每个人工任务必须包含：缺什么、系统试过什么、为什么不能自行继续、推荐决定、其他选择及影响。

## 6. 资料获取如何接入命题

### 6.1 获取请求

编排器基于冻结范围为资料获取模块提交版本化请求，至少包含：

- `case_id`、`scope_version`、`research_run_id`；
- 命题和关键因素的稳定 `goal_id`；
- 每个目标所需的支持证据、反向证据或替代解释；
- 主体、指标、时间窗和 HistoricalBasis cutoff；
- 允许来源角色和 SourcePolicy 版本；
- 当前缺口和前轮已覆盖来源；
- acquisition round 和幂等键。

### 6.2 命题驱动获取循环

```text
选择最高优先级证据缺口
→ 生成或读取冻结检索计划
→ 搜索真实来源
→ 获取原始内容
→ 规范 URL 与内容哈希去重
→ 来源治理与自动准入
→ 冻结 DocumentVersion
→ 重算每个 goal 的覆盖
→ 达标、继续下一轮或请求边界决定
```

每一次搜索必须关联 `goal_id` 和 query plan，不能只记录一个普通关键词。

### 6.3 搜索可变性与可重放性

外部搜索结果会随索引、披露和来源可用性变化。系统不承诺不同时间的搜索结果完全相同，而承诺同一次运行可重放、证据不可静默改变、运行之间的差异可解释。

硬规则：

1. 基础查询由冻结的主体、关键因素、时间窗和来源规则生成；
2. 模型只能针对明确缺口生成受约束扩展查询，不能改变 SourcePolicy 或研究方向；
3. query plan 保存输入、查询、planner/model/prompt 版本、参数和来源范围；
4. 同一次运行的技术重试必须复用已冻结 query plan，不重新随机生成；
5. 只有创建新 acquisition round 才能扩展查询，并记录与上一轮的差异和触发原因；
6. 每次 search 保存原始结果列表；每次 fetch 保存原始响应、时间、最终 URL 和哈希；
7. 来源内容改变时创建新版本，不覆盖旧 RetrievalArtifact 或 DocumentVersion。

`AcquisitionJob` 保持“一轮一个不可变请求”。同一个 tenant、Case、research run、scope version、thesis 和 `goal_id` 由稳定的 `AcquisitionSeries` 聚合；每轮计划属于独立 Job，但其前驱必须是同一 Series 的上一轮计划。技术重试仍留在当前 Job，绝不创建新计划。

### 6.4 来源适配器

统一 `SourceAdapter.search/fetch` 协议承载来源差异。当前 SSE/SZSE adapter 是内核起点，后续按 SourcePolicy 逐项接入：

- CNINFO；
- HKEX / SEC 等监管披露；
- 已登记公司的官方 IR；
- 有真实许可的授权研究源；
- 受治理的通用网页发现能力，仅作为候选线索，默认不能替代高权威原文。

来源必须有真实搜索和获取能力才算 adapter。禁止用通用抓取器加 URL 参数伪装成受治理来源。

## 7. 资料达标与准确性

### 7.1 覆盖判定

资料是否足够按每个研究目标判断，不按总资料数判断。必要门槛至少包括：

- 所有关键因素达到规定覆盖；
- 需要一手披露的目标满足权威层级；
- 已主动搜索可推翻主命题的反向证据；
- 资料位于冻结时间窗，主体、期间、单位和指标一致；
- 重复转载不作为独立来源重复计数；
- 关键外部事实达到策略规定的独立来源交叉验证要求；
- 仍未解决的冲突和缺口被明确保留。

覆盖结果只有三类：

- `ready`：必要目标满足，自动进入证据归并；
- `needs_decision`：关键目标未满足，继续需要改变研究边界；
- `exhausted`：连续限定轮次没有新增独立资料，停止假推进并保留未知项。

### 7.2 准确性边界

系统不能保证自动结论等同于客观真相。它必须保证：

- 结论只能使用已冻结、已准入且能回到原文定位的证据；
- 支持、反向和不确定性同时呈现；
- AI 输出必须经过来源、时间、语义和结构化一致性门禁；
- 置信度不能单独完成准入；
- 证据不足时输出“未知”或“尚不能下结论”，不能根据搜索摘要补全事实；
- 未经人工审核的报告持续带有明确标识。

## 8. 重试、恢复和停机语义

### 8.1 系统自行处理

对瞬时错误按以下顺序处理：

```text
同源重试 → 切换允许来源 → 扩展查询 → 重算覆盖
```

重试采用指数退避、来源限流规则、租约 fencing 和 per-reference 错误隔离。单一资料失败不阻塞整轮获取。

### 8.2 API / worker / scheduler 恢复

- PostgreSQL 是唯一恢复依据，进程内状态不承担正确性；
- 每个任务有 `lease_owner`、`lease_token`、`lease_expires_at` 和心跳；
- worker 只能用当前 lease token 提交结果；
- scheduler 扫描过期租约并按原幂等键重新入队；
- API 重启后 workflow projection 直接读取持久化阶段和检查点；
- Research Worker 重启后读取已有 acquisition job，不重复创建；
- Acquisition Worker 重启后从最后一个已提交阶段继续；
- 页面在失联期间显示最后心跳、失败阶段和恢复计划，不能回退为模糊的“运行状态暂不可确认”，也不能用旧 Case 状态冒充实时运行。

## 9. 身份、权限和服务端 Actor

所有受保护写操作遵循：

```text
登录会话 / JWT → UserPrincipal → CaseGrant → server_actor
```

- 创建 Case 的用户自动成为 owner；
- 用户只能访问已授权 Case；
- `actor`、`reviewer`、`approved_by` 等身份字段从客户端命令 DTO 移除或被服务端拒绝；
- 人工 actor 为 `user:<internal_user_id>`；
- 系统 actor 关联 worker 类型、实例和 run id；
- 每个编排转换和人工决定都记录 principal、Case、权限和决策结果。

## 10. 统一查询和命令接口

事件工作台至少需要一个统一 workflow projection，返回：

- 当前事件、命题和 `scope_version`；
- 用户可见阶段及内部状态；
- 当前系统动作、原因、开始时间和心跳；
- 已完成阶段和最近过程事件；
- 当前唯一用户动作，可为空；
- acquisition 目标覆盖、来源计数和资料台账摘要；
- 报告状态、监测状态和系统生成标识；
- 可恢复状态、最后检查点和下一次重试时间。

命题确认、用户边界决定、主动停止和可选复核使用显式命令接口。命令只提交业务选择和客户端幂等键，不提交可信身份或下一状态。

实时展示可以使用 SSE 或短轮询，但两者必须读取同一个服务端 projection 和追加式事件源。连接失败只影响实时性，不能改变业务状态。

## 11. 可直接启动和监控的拓扑

默认 Compose 拓扑包含：

- `postgres`；
- `keycloak` 或等价真实身份提供方；
- `migrate`；
- `api`；
- `research-worker`；
- `acquisition-worker`；
- `scheduler`；
- `frontend`。

统一应用镜像使用不同启动命令运行 API 和 worker。健康检查区分 liveness 与 readiness；迁移失败时应用不得 ready。运行状态和结构化日志能按 `case_id`、`research_run_id` 和 `acquisition_job_id` 串起完整轨迹。

## 12. 不使用 Mock 的真实浏览器主链验收

### 12.1 约束

- 前端使用生产 HTTP adapter，Mock 开关关闭；
- 浏览器通过真实身份页面登录；
- Case、资料、范围和决定都通过 UI 或公开 HTTP 命令产生；
- 验收脚本禁止 SQL/ORM 写入或读取业务结果；
- 使用真实 API、worker、scheduler、PostgreSQL 和来源 adapter；
- 进程故障通过 Compose 控制面注入，不修改数据库状态；
- 缺少 live provider 凭证或来源不可用时明确 skipped/unavailable，不能回退 fixture 后声称真实验收通过。

### 12.2 场景 A：完整成功主链

1. 使用真实测试账号登录；
2. 从页面新建事件 Case；
3. 上传真实 PDF 或粘贴真实资料；
4. 确认命题和研究范围；
5. 验证系统自动创建 Research Run 和 AcquisitionJob；
6. 在事件工作台看到查询、真实来源、获取、冻结、去重和覆盖过程；
7. 验证系统自动完成证据归并、命题判定和报告生成；
8. 未经人工审核的报告显示明确标识，并自动进入持续监测；
9. 从报告结论回到冻结原文和获取记录。

### 12.3 场景 B：真实重启恢复

在同一次主链中：

1. 创建 acquisition job 后重启 API；
2. 至少冻结一份资料后强制终止 acquisition worker；
3. 证据已准入、报告尚未形成时重启 research worker；
4. scheduler 从过期租约恢复任务；
5. 浏览器只通过公开状态观察恢复，最终主链完成。

验收必须证明没有重复 DocumentVersion、EvidenceLink、报告版本或副作用事件。

### 12.4 场景 C：资料不足

1. 触发一个无法在当前来源边界内满足的关键证据目标；
2. 验证系统完成限定的同源重试、切源、查询扩展和覆盖检查；
3. 页面展示缺口、尝试历史、推荐选择和唯一用户动作；
4. 用户决定扩大或维持边界；
5. 扩大边界时生成新 `scope_version`、新 acquisition round 和查询差异；维持边界时以 exhausted 或证据不足完成，不假装已有结论。

### 12.5 每次验收的证据包

- 关键页面截图和 DOM 状态；
- Research Run、阶段事件、检查点、重试和恢复记录；
- query plan、真实来源、响应摘要、哈希和去重血缘；
- 容器健康、重启时间、worker 租约和 scheduler 恢复动作；
- 环境、代码版本、SourcePolicy、provider 和执行时间。

## 13. 实施顺序

1. 建立 `ResearchOrchestration`、统一 projection、追加式事件和原子 outbox；
2. 将命题确认命令接到 acquisition request，增加目标覆盖和冻结 query plan；
3. 将 acquisition terminal 状态接回证据归并、命题判定、报告和监测；
4. 将事件工作台改成已确认的组合结构，并接入真实 projection；
5. 完成 API、worker、scheduler、PostgreSQL、身份和前端的统一拓扑；
6. 建立 no-Mock、no-direct-DB 的 live browser acceptance 和进程故障注入；
7. 逐项删除客户端 actor、旧 Case 状态回退和需要用户手动“继续”的遗留路径。

每一步先增加失败测试，再实现最小闭环；不能只让页面看起来连通。

## 14. 非目标

- 第一版不引入 Kafka、Temporal 或独立消息总线；
- 第一版不把 acquisition 拆成独立数据库或微服务；
- 不保证不同时间的外部搜索结果完全一致；
- 不用资料数量、模型置信度或运行成功状态冒充研究结论；
- 不要求所有证据或报告默认人工审核；
- 不在本规格提交中修改用户当前未提交的前端样式、测试或其他计划文件。

## 15. 完成标准

完成后，一个新用户能够只通过事件工作台走完：

```text
新建事件 → 上传资料 → 确认命题 → 离开页面也会自动补证
→ 随时看到系统正在做什么和做过什么
→ 只在必要时处理一个决定
→ 获得可回溯、带审核状态的系统报告
→ 进入持续监测
```

API、research worker、acquisition worker 任意重启后，这条流程仍从真实检查点继续；真实浏览器验收不使用 Mock、不直接操作数据库，并能保存足以复现问题的完整证据包。
