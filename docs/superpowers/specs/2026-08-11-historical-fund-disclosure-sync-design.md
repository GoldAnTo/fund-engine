# 历史基金披露同步期次冻结设计

## 目标

为 ResearchCase 的基金历史披露补充提供可回放的单期同步。配置必须冻结基金代码、当前 Case 已审核股票和目标报告期；运行只读取并写入该期次的历史披露，不能把“最近一期”或未来报告期混入历史案例。

## 已确认问题

当前同步查询固定使用“最近一期公开披露的股票持仓明细”。对 `515050` 的实际供应商响应含 2025 至 2026 年的六个报告期及 `.OF`、`.SH` 代码表示。同步器会按返回的每个分组继续检索基金公告，既不能复核案例所需的 2024Q4，也会扩大数据范围和请求数量。

运行状态由最后一条事件推导。若供应商工作被中断在 `query_holdings` 后，当前记录没有终态事件，页面会永久显示 `started`。

## 范围

1. 为 `FundDisclosureSyncConfigVersion` 增加可选但一经配置不可变的 `report_period`（ISO 日期）。历史案例配置 `2024-12-31`。
2. 同步请求改为带目标期次的查询，并在解析后按规范化基金代码和目标报告期二次过滤。只有完全匹配的数据可进入公告匹配和披露写入。
3. 配置或运行指定期次时，未匹配的返回行记为范围外/无效统计，不得触发未来期次公告查询。
4. 为运行增加可恢复终态：供应商超时、取消或任何非正常退出均追加失败事件。读模型将没有终态且超过短暂执行窗口的旧记录显示为可重试失败，而不是永久执行中。
5. 前端配置表单显示“目标报告期”；对已有历史披露建议默认使用建议项的最近报告期，人工可修改。运行记录显示冻结期次。

## 明确不做

- 不推断实时持仓、完整基金组合或基金推荐。
- 不创建自动调度任务；频率仅是现有配置模型的必填字段。
- 不改变 2024Q4 以外的已有 HoldingDisclosure，也不删除已保留的错误运行审计事件。
- 不将历史预测案例升级为全 Case 持续监控。

## 数据与错误处理

配置保存时必须校验 `report_period` 为有效日期。执行时构造显式“基金 + 报告期”的 FinQuery，过滤后的行再按同基金、同报告期查找唯一基金季报。运行事件记录目标期次、原始行数、范围外行数、匹配季报和写入/去重数。

执行入口在开始外部调用前保留范围事件；任何 `BaseException` 以外的供应商、解析或写入失败都写入 `failed`。调用端若请求中止，后台恢复检查将为遗留 `started` 运行追加 `interrupted` 失败事件，以其冻结范围支持重试。

## 验收

1. `515050` / `2024-12-31` 的真实运行只查询和写入该期次；响应中 2025–2026 行不触发公告查询。
2. 运行页面显示冻结基金、股票、报告期、供应商能力、原始/范围外行数、公告匹配和最终结果。
3. 模拟中断的运行有可见失败终态并可按原配置重试。
4. 旧的未终态记录不再在活动任务中永久显示为执行中。
5. 后端同步、API 和前端任务组件测试，以及生产构建均通过。
