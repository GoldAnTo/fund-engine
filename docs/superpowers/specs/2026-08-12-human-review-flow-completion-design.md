# 人工审核流程闭环设计

日期：2026-08-12

## 背景

当前原型中的证据审核写操作只会从审核队列移除候选。事件工作台、生命周期、进度统计和顶部运行状态仍保留审核前的数据，因此用户完成操作后仍看到“等待人工审核”，无法判断流程是否前进，也无法继续完成后续任务。

本次修改只修复本地原型适配器和对应页面反馈，不改变真实后端接口契约。

## 目标

人工处理证据候选后，系统必须形成一个可继续执行的状态闭环：

1. 审核决定被记录。
2. 审核队列、证据统计、事件生命周期和运行状态同步更新。
3. 页面自动回到事件工作台。
4. 工作台明确显示刚才发生了什么、现在处于哪一阶段、下一步由谁执行。
5. 后续人工任务可以继续完成，不出现已清空队列但状态仍停留在“等待人工审核”的死路。

## 状态转换

### 确认采纳

- 候选从待审核队列移除并计入已审核证据。
- 当前因素的待审核数归零，已审核支持数增加。
- 事件从 `awaiting_key_review` 转为 `draft_ready`。
- 研究阶段从“审核证据”进入“形成结论”。
- 下一步人工任务变为“审核结论草案”。
- 主研究运行从 `waiting_for_review` 转为已完成状态，不再显示等待人工审核。

### 要求补充证据

- 候选从当前审核队列移除，审核决定保留为“需要补证”。
- 事件转为 `researching`。
- 当前缺口更新为审核理由所表达的补证需求。
- 下一步由系统执行，工作台显示“系统补证中”，不制造虚假的人工任务。
- 主研究运行进入执行中的补证阶段。

### 驳回候选

- 候选从当前审核队列移除并保留驳回记录，不计入已审核支持证据。
- 事件转为 `exhausted`，因为当前冻结范围内不再有可采纳候选。
- 当前缺口明确为“当前候选被驳回，需要调整因素或补充来源”。
- 下一步人工任务变为“编辑并继续自动研究”。
- 主研究运行结束当前轮次，不再显示等待人工审核。

## 数据设计

原型适配器为每个事件维护审核后的可变状态，至少包含：

- 最近一次审核结果与理由；
- 已审核证据数量；
- 待审核数量；
- 生命周期状态、摘要、缺口和下一人工动作；
- 结论状态；
- 与事件关联的原型运行状态。

`reviewProposal` 是状态转换的唯一入口。`getEventReviewQueue`、`getEventWorkbench`、`listEventResearch` 和原型运行读取接口都从同一份转换结果派生展示数据，避免各自保留互相矛盾的静态 fixture。

## 页面行为

提交审核成功后，审核页显示短暂的成功反馈，然后导航到当前事件的研究结论页。事件工作台重新读取最新状态，并在“你需要做”区域展示新的动作：

- 确认采纳后：审核结论草案；
- 要求补证后：现在不用做，系统补证中；
- 驳回后：编辑因素并继续研究。

提交失败时保留理由输入和当前候选，不导航、不提前更新进度，并显示可重试错误。

## 测试

### 适配器状态转换测试

分别验证三种审核结果，断言队列、工作台、事件列表和运行状态来自同一状态转换。

### 页面集成测试

从事件工作台进入审核页，填写理由并提交，断言自动返回事件工作台并看到正确的新阶段、进度和下一步任务。

### 端到端测试

在 mock 开发模式中完成“台积电事件 → 证据审核 → 确认采纳 → 结论复核入口”的完整人工路径，确保没有死路。

## 非目标

- 不在本次修改中重做真实后端研究运行状态机。
- 不新增证据审核结果类型。
- 不自动发布最终结论；结论草案仍必须由人工复核。
- 不把原型状态写入持久数据库；重启开发服务后允许恢复初始 fixture。
