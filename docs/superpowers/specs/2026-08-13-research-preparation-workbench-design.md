# 研究准备工作台设计

## 背景

当前事件研究创建成功后直接进入 Case 结论页。页面会显示阶段、关键因素和“核验冻结原文”等入口，但用户无法清楚判断：系统此时是否正在工作、正式研究是否已经启动、自己现在应该做什么。

后端现状同样存在语义缺口：创建流程会冻结资料、建立 Case、范围和关键因素，但不会继续解析原文、生成研究协议草案或补证计划。页面却容易让用户误以为系统正在后台核验和研究。

本设计在 Case 创建和正式 `ResearchRun` 之间增加独立的“研究准备”阶段。系统自动准备可供审核的草案，用户逐项确认后才明确授权正式研究。

## 目标

- 新建 Case 后立即告诉用户系统在做什么，以及当前是否需要人工操作。
- 自动解析冻结原文，生成候选原子陈述、研究协议草案和补证计划。
- 保持严格的人机边界：系统只准备草案，不采纳、不批准、不执行补证。
- 用户按固定顺序确认三类产物，最后明确授权后才创建 `ResearchRun`。
- 自动准备过程可观察、可恢复、可重试，并保留完整的版本和活动记录。
- 为既有尚未启动的 Case 自动补齐相同准备流程。

## 非目标

- 不在用户授权前调用数据 Provider 执行正式补证。
- 不自动批准原子陈述、研究协议或补证计划。
- 不用准备任务冒充 `ResearchRun`，也不复用正式研究状态表达准备进度。
- 首版不引入 WebSocket；使用轮询和游标增量日志满足实时反馈。
- 不重新设计正式研究、证据审核和结论发布流程。

## 已确认的用户流程

```mermaid
flowchart LR
    A["冻结资料并创建 Case"] --> B["自动解析原文"]
    B --> C["生成研究协议草案"]
    C --> D["生成补证计划"]
    D --> E["用户核验原文与候选陈述"]
    E --> F["用户确认研究协议"]
    F --> G["用户审核补证计划并明确授权"]
    G --> H["创建唯一 ResearchRun"]
    H --> I["启动正式补证"]
```

Case 创建完成后跳转到：

`/events/:caseId/preparation`

准备和确认必须按以下顺序完成：

1. 核验冻结原文与候选原子陈述；
2. 确认研究协议；
3. 审核补证计划并明确授权启动。

在第三步授权成功前，页面和 API 必须始终如实表达：

- `ResearchRun 未创建`；
- `后台正式研究尚未启动`；
- 自动准备产物仍是草案。

## 自动准备的职责边界

### 系统自动完成

#### 原文解析

- 读取创建时冻结的原文版本和可用范围。
- 提取候选原子陈述及其原文定位。
- 保留候选与来源片段的对应关系。
- 只创建候选，不创建已经通过人工审核的正式陈述。

#### 研究协议草案

- 建议目标指标和结果判定口径。
- 建议研究范围、基线和观察时间窗。
- 建议机制、必要边和反证方向。
- 保存为准备产物，不直接写入已批准的正式协议对象。

#### 补证计划

- 按关键因素列出待验证目标。
- 建议允许的数据来源和 Provider 类别。
- 给出优先级、预算、停止条件和预期产物。
- 保存为草案，不创建任务、不调用 Provider、不启动正式补证。

### 系统不得自动完成

- 采纳或拒绝候选原子陈述；
- 批准结果绑定、机制模板或验证规则；
- 授权数据 Provider 执行补证；
- 创建或推进正式 `ResearchRun`；
- 将自动草案包装成已经确认的研究事实。

## 领域模型

准备流程独立于 `ResearchRun`，引入三个核心对象。

### ResearchPreparation

表示某个 Case 当前有效的准备实例和编排状态，至少包含：

- Case 和租户归属；
- 当前版本与输入指纹；
- 原文解析、协议草案、补证计划三个系统步骤状态；
- 三个人工确认步骤状态；
- 当前有效产物版本；
- 重试信息、更新时间和最后安全错误；
- 是否已经完成授权以及关联的唯一 ResearchRun。

同一个 Case 同一时间只能存在一个当前有效的准备版本。

### ResearchPreparationArtifact

保存追加式、不可原地覆盖的版本化产物：

- `atomic_claim_candidates`；
- `research_protocol_draft`；
- `evidence_acquisition_plan`。

每个产物记录：

- 输入指纹和准备版本；
- 结构化内容；
- 生成时间和生成来源；
- 是否当前有效；
- 失效原因和被哪个版本替代；
- 人工确认、修改或拒绝结果。

### ResearchPreparationEvent

保存追加式活动日志，面向研究人员表达完整过程：

- 步骤开始、完成、失败和重试；
- 输入范围和产物数量；
- 执行时间、耗时和尝试次数；
- 人工确认、修改和授权；
- 下游失效与重新生成原因；
- 安全、稳定的错误类别和说明。

日志不得保存或返回密钥、授权头、原始 Provider 错误、敏感 URL、完整响应体或受许可限制的原始载荷。

## 状态模型

系统步骤采用统一状态：

- `queued`：已排队；
- `running`：正在执行；
- `succeeded`：当前版本完成；
- `retrying`：等待自动重试；
- `failed`：重试耗尽，等待人工处理；
- `stale`：上游输入变化，当前产物失效。

人工步骤采用：

- `locked`：上游尚未完成或确认；
- `awaiting_review`：当前需要用户处理；
- `confirmed`：已完成当前版本确认；
- `stale`：上游修改后原确认失效。

准备流程对外汇总为：

- `preparing`：系统正在准备，用户无需操作；
- `awaiting_claim_review`：等待核验候选原子陈述；
- `awaiting_protocol_confirmation`：等待确认研究协议；
- `awaiting_plan_authorization`：等待审核计划并授权；
- `recoverable_failure`：自动准备失败，可重试；
- `authorized`：已授权并创建 ResearchRun。

## 版本、失效与重新生成

每个产物都绑定明确的输入指纹：

- 原文解析绑定冻结资料版本和解析范围；
- 协议草案绑定已确认或当前候选陈述版本及 Case 范围；
- 补证计划绑定协议草案、关键因素和约束版本。

如果用户修改或拒绝上游陈述：

1. 已完成的原文核验保存为新版本；
2. 依赖旧输入的协议草案和补证计划标记为 `stale`；
3. 只重新生成受影响的下游产物；
4. 页面保留新旧版本和失效原因；
5. 用户必须重新确认受影响的步骤。

迟到的 Worker 输出如果输入指纹或准备版本已经过期，只记录为被丢弃的旧结果，不得覆盖当前产物。

## 后台执行与恢复

### 新建 Case

创建 Case、冻结原文和创建准备任务必须处于可靠的同一业务事务边界。事务提交后 Worker 才执行外部调用，避免出现 Case 创建成功但准备任务永久丢失的状态。

### 既有 Case 回填

部署后由幂等扫描器自动发现符合条件的 Case，而不是在数据库迁移中调用外部服务。候选条件为：

- 已完成租户准入并有冻结资料；
- 尚未发布；
- 从未创建正式 ResearchRun；
- 没有有效的准备实例。

回填按 Case 创建时间由早到晚、分批排队。已有候选、人工审核或协议数据应尽量复用，不覆盖已有人工结果。

### 重试

- 每个系统步骤独立有限重试；
- 使用可配置的指数退避；
- 已完成产物不因下游失败而删除；
- 重试只执行失败步骤及其必要下游；
- 自动重试耗尽后展示人工重试入口；
- 人工重试会创建新的尝试记录，不修改历史事件。

## 并发与幂等

- 所有准备状态变更遵循稳定的 Case 到 Preparation 锁顺序。
- Worker 领取步骤时同时校验当前版本、输入指纹和输出槽位。
- 同一 Case、同一准备版本、同一步骤最多有一个有效执行者。
- 人工确认使用版本条件更新，过期页面提交返回冲突并要求刷新。
- 最终授权必须是幂等操作；重复点击、网络重放或并发请求最多创建一个 ResearchRun。
- 授权事务内冻结正式补证计划、记录授权事件并建立 ResearchRun 关联。
- 如果另一事务已经完成授权，后到请求返回同一个有效结果，而不是创建重复 Run。

## 页面信息架构

### 顶部状态区

页面标题为“研究准备”，不是“研究结论”或“证据审核”。顶部显示：

- Case 标题与资料版本；
- 当前准备状态；
- 当前步骤和总体进度；
- `ResearchRun 未创建 / 后台正式研究尚未启动`；
- 授权完成后改为关联 ResearchRun 状态和入口。

### 桌面布局

采用双栏布局：

- 左侧为完整系统活动时间线；
- 右侧只显示当前状态或当前一项人工任务。

系统准备中时，右侧明确写“现在不用做”，说明当前步骤和准备完成后将要求用户确认什么。

准备完成后，右侧原位切换为当前人工步骤：

1. 候选原子陈述核验表单；
2. 研究协议确认表单；
3. 补证计划审核与授权表单。

后续步骤可以预览，但保持锁定，不允许跳步操作。

### 活动时间线

默认完整展示，不隐藏关键步骤。每条记录至少表达：

- 正在或已经完成的事项；
- 输入范围；
- 产物与数量；
- 开始时间、完成时间或耗时；
- 当前尝试次数；
- 失败时的安全错误和下一次重试时间。

技术标识可以通过详情查看，但不得让内部 ID 成为主视觉内容。

### 失败状态

失败卡片显示：

- 哪一步失败；
- 哪些已有产物仍然有效；
- 系统是否还会自动重试；
- 下次重试时间或“手动重试”按钮；
- 不影响上游已确认内容的说明。

### 响应式与可访问性

- 窄屏下先显示当前状态或当前任务，再显示活动时间线；
- 中文长标题、因素和协议条款允许自然换行；
- 所有步骤、按钮和错误状态均支持键盘操作和明确焦点；
- 状态不能只依赖颜色，需要图标或文字；
- 执行中变化使用非侵入式状态提示，不抢夺焦点；
- 尊重减少动态效果设置。

## Research Desk 联动

Research Desk 必须区分系统任务和人工任务：

- `preparing`：系统处理中，不计入“待我审核”；
- 三个 `awaiting_*` 状态：进入“待我审核”，显示明确步骤和数量；
- `recoverable_failure`：进入需要处理的恢复任务；
- `authorized`：按现有正式研究生命周期展示。

用户从 Desk 或 Case 导航重新进入时，直接定位到第一个未完成的人工确认步骤。现有未启动 Case 进入相同准备工作台，不再停留在含糊的结论页。

## API 边界

API 至少需要支持：

- 获取当前准备摘要、步骤状态和有效产物；
- 使用游标增量读取活动事件；
- 提交候选陈述核验结果；
- 提交协议确认或修改；
- 提交补证计划确认并明确授权；
- 对失败步骤发起人工重试；
- 查询 Desk 所需的准备状态与下一人工动作。

执行中页面采用轻量轮询：摘要按固定间隔刷新，事件按游标增量加载。页面离开不会取消后台准备。

所有写接口必须校验租户、Case、准备版本和当前允许的步骤，不能仅依赖前端锁定状态。

## 视觉方向

- 延续 Fund Engine 现有克制、专业、研究型视觉语言。
- 使用温和的中性色、现有绿色主色和明确但不过度醒目的状态色。
- 视觉重心是当前状态、人机责任边界和唯一操作，不增加营销插画。
- 活动推进参考 Linear 的清晰任务状态；执行日志参考 GitHub Actions 的步骤、时长和重试表达。
- 页面保持安静、信息密度适中，避免同时出现多个同等权重的主按钮。

## 验收标准

### 后端

1. 新建 Case 后可靠创建并排队准备流程，且授权前不存在 ResearchRun。
2. 三类草案按顺序生成并保存为版本化产物，不被自动采纳或批准。
3. 步骤失败仅重试失败步骤及必要下游，已完成产物保持可用。
4. 上游修改准确使依赖产物失效，旧 Worker 输出不能覆盖新版本。
5. 人工确认严格按顺序执行，过期提交被拒绝。
6. 授权在并发和重放下只创建一个 ResearchRun。
7. 既有未启动 Case 回填幂等、可分批恢复且不覆盖人工数据。
8. 全部接口和日志满足租户隔离与 Provider 错误脱敏要求。

### 前端

1. 新建成功立即进入研究准备页，而不是结论页。
2. 准备中明确显示系统工作和“现在不用做”。
3. 用户始终只看到当前一项主要任务，并能预览锁定的后续步骤。
4. 完整活动日志展示步骤、产物、耗时、重试和安全错误。
5. 上游修改后页面明确解释下游失效和重新生成。
6. 准备失败、自动重试、人工重试和恢复状态均有独立呈现。
7. Desk 计数、路由和重新进入位置与准备状态一致。
8. 窄屏、键盘、焦点、长文本和非颜色状态表达通过测试。

### 集成

1. 使用本地 OpenAI-compatible 测试 Provider 走通完整自动准备流程。
2. 自动准备完成后仍无 ResearchRun；第三步授权后恰好创建一个 Run。
3. Provider 失败不会形成模拟成功，错误不泄漏凭据或原始响应。
4. 进程中断后可从持久状态恢复，不重复产物或授权。

## 上线与迁移

- 数据库迁移只增加准备相关结构、约束和索引，不发起外部调用。
- 上线后启用准备 Worker 和幂等回填扫描器。
- 前端新路由上线后，新 Case 直接进入准备页；符合条件的旧 Case 也路由至该页。
- 可以分批开启旧 Case 回填，但人机边界和授权门禁不能通过功能开关绕过。
- 监控准备队列积压、步骤失败率、平均耗时、重试次数、待人工确认数量和授权转化，不记录敏感 Provider 内容。

## 已解决的设计选择

- 使用独立准备域，不提前创建 ResearchRun。
- 自动准备三类草案，但所有采纳和执行均由用户确认。
- 使用完整活动时间线和单一当前任务布局。
- 系统处理中不制造人工待办；准备完成后产生明确待确认任务。
- 既有未启动 Case 自动回填，而不是等待用户首次打开。
- 使用有限重试、产物保留、版本失效和精确下游重生成。
- 首版采用轮询与游标日志，不引入 WebSocket。
