# 事件研究：可审核证据与来源准入设计

## 目标

让研究员在审核关键证据时，始终能回答四个问题：还要审核多少条、这条证据为何与当前因素有关、来源能否实际核验、点击某个决定会怎样改变研究流程。

## 现状问题

当前页面只展示一条证据，没有全量或进度；“采纳”没有说明其台账与结论后果；来源以纯文本 URL 展示且不能打开。更严重的是，事件研究可从全局历史资料中召回 `example.test` 等测试材料，导致不可验证材料看起来像真实研究证据。

## 设计决策

采用“待审清单 + 单条详情”的混合审核页。

### 页面结构

顶部进度带展示：本轮待审总数、已处理数、剩余数、当前轮次，以及处理完成后的下一步。示例：`第 1 轮 · 关键证据 4 条 · 已处理 1 条 · 待处理 3 条`。

左侧清单按待审顺序列出每条证据，显示：序号、关联因素、证据方向、来源标题或域名、来源状态。当前条高亮；研究员可主动切换，不必反复点击后才知道下一条。

右侧详情仅呈现当前条：原文摘录、来源标题、可打开链接、原文定位、发布日期和可用时间、AI 提议该证据支持或反驳哪个因素的理由。

### 来源状态与准入

来源状态是系统明确字段，不由研究员自行猜测：

1. `官方原始来源`：公司公告、监管披露、财报或电话会原文，可打开，可采纳。
2. `可访问的二级来源`：信誉媒体、研究机构、转载稿，可打开，可采纳，但在结论中保留来源层级。
3. `受限来源`：链接可识别但需登录、失效或抓取失败，不能采纳；研究员可退回并要求补充原始材料。
4. `不可验证来源`：空链接、无定位、测试域名（包括 `example.test`、`example.com`）、本地 fixture 或跨事件错误材料，不能采纳，必须退出本事件审核队列并记为无效来源。

链接以安全的新标签页方式打开，并在 UI 中同时保留 URL 文本。打开失败不能自动把来源标为可信。

### 审核动作

按钮使用结果导向文案：

- `采纳为本因素的正式证据`：仅对可采纳来源启用。写入已审核证据集，成为未来结论可引用的依据；不表示最终因果结论成立。
- `不采纳，不计入结论`：记录该材料已被人工排除，不再作为当前事件的候选依据。
- `退回并继续找真实来源`：保留当前研究缺口，触发或排队后续检索，不把材料写入结论依据。

每次操作后，进度带立即更新，并展示下一条或“本轮已处理完，系统正在继续研究/准备结论草案”。

### 数据与隔离规则

事件创建时，粘贴的新闻与 URL 必须先形成该事件自己的来源记录。自动研究仅可检索与该事件显式关联、且通过来源准入的材料；不得召回其他事件或历史测试 fixture 的 SourceStatement。

测试 fixture 的 URL 使用独立标记或测试环境数据，不得进入开发环境的真实待审队列。已有包含不可验证来源的待审提议，保留审计痕迹但从人工可采纳队列移除，并标记为 `invalid_source`。

## 接口与前端契约

审核队列返回整个事件范围的项目集合与汇总：`total`、`reviewed`、`pending`、`invalid_source`、`current_round`、`next_action`。每个项目补充 `source_title`、`source_url`、`source_status`、`source_status_reason`、`proposal_reason` 和顺序。

前端不再用“提议列表的第一条”猜当前证据。它按稳定排序读取队列，选中的 `proposal_id` 与详情严格对应。

## 验收标准

1. 研究员无需点击按钮即可知道总量、已处理量、待处理量和完成后的系统动作。
2. 每条证据的来源能打开，或明确说明为何不可访问。
3. 不可验证或测试来源没有“采纳”入口，且不会进入结论引用。
4. 采纳、不采纳、退回三种动作的台账和后续流程效果可见且可测试。
5. 新事件只能使用本事件关联的合格来源；跨事件和 fixture 来源被拒绝。
6. 真实审核端到端测试覆盖 PostgreSQL 外键约束与来源准入，前端测试覆盖进度、禁用态、按钮文案和来源链接。
